## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole session). Refusal errno is contract: EPERM degrades, EINVAL/ENOSYS fails hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check. Never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A `SharedUnixAddrPresenceTable`-shaped mutable table needs every write path mirrored to the shared side.
- **`(dev, ino)` is NOT a cross-process-stable file identity in litebox.** A fork child rebuilds its fs from the parent's exported writable layer, so `InodeAllocator` renumbers every runtime-created file: measured `dev` equal (1283027571) but `ino` 527 in the parent vs 1 in the child. **Any shared registry keyed on `(dev, ino)` cannot exclude across processes.** Key on `(dev, path)` (`FilesState::lookup_fd_path`).
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`); carried: pipes/regular files/eventfds/pty/unix sockets; **on `inetfix` (now main) also INET sockets (`9997313`) and `MAP_SHARED` mappings (`a629714`)** -- both halves of the old "NOT carried at all" clause are FALSE; dropped: pty fds and non-INET cloexec fds. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6) gates the spawn and fails open after 8s, because each child rebuilds the OCI rootfs in its own heap. Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it. The post-duplication clone site is SUPERSEDED -- believe `try_cross_process_fork`'s log.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot roots every task sharing that state, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets. Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`, `LITEBOX_PROCESS_FORK_IGNORE_FDS`, `LITEBOX_DIAG_FORK_SHARED_FORCE_FAIL`, `LITEBOX_FLOCK_SHARED_OFF`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Subagents: Sonnet, not Opus. Web search: Google, not DDG (camoufox if blocked).

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` blocks a host thread on the child's INITIATING THREAD handle, then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. `sys_wait4` re-polls every 15ms; on reap it runs `import_cross_process_writable_layer`. `waitpid(-1)` only sees entries registered in THIS host process -> ECHILD. **SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything reaping off SIGCHLD alone (glib) can miss it**; `signalfd` never wakes (`signalfd.rs:185-191`); `pidfd_open` (`inotify.rs:353`) does. **The external fault watchdog polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s** (sticky event `Local\litebox-fault-armed-<pid>`; NULL `OpenEventW` = ALWAYS ARMED); LATENT false positive.

## Guest stack: chromium + selkies

- **TWO chromium failure modes -- do not merge them.** (a) `Crashing due to FD ownership violation:` + `zygote_host_impl_linux.cc:129] No usable sandbox!` = the `CanCreateProcessInNewUserNS()` probe. (b) rc=133 (SIGTRAP) with NO sandbox line = crashpad/HOME.
- **A `HOME` chromium shares with anything root ran kills it**: a root-run app makes `$HOME/.config` 0755 root, so uid 911 gets `stat .../Crash Reports: Permission denied (13)`; crashpad mkdirs only its LAST component, so a missing chain is ENOENT (2). Fix: `mkdir -p $HOME/.config/chromium; chmod -R 777; chown -R 911:911` on a HOME nothing else touched -- `chmod 777` on a SHARED HOME is NOT enough. chrD61's `PREP_LS` prints the chain before launch.
- NON-ROOT (`setpriv --reuid 911 --regid 911 --init-groups`); `--user-data-dir` `chmod 777` when a root shell created it (else `SingletonLock: Permission denied`, exit 21). `HOME=/tmp/cuhome` exits 0 (`cpad1.sh`); `--crash-dumps-dir` does not exist in Debian's build.
- `seccomp(2)` is real: `syscalls/seccomp.rs` interprets classic BPF at the top of `Task::do_syscall`; `SECCOMP_RET_TRAP` must RETURN the syscall number (`ad2659f`), payload in `si_errno` (`067367b`).
- Still open: (1) the launcher thread SERIALISES cross-process spawns, so children hit the 15s "no connection" self-termination; (2) `Vmem::duplicate` skips `VM_OWN_FORK_PADDING`; (3) ~1/run `rebuilding a carried SCM_RIGHTS fd failed errno=ENOENT`; (4) two simultaneous chromiums are not affordable -- run ONE.
- **CDP from inside the guest is the decisive chromium probe** (`chrdesk38.sh`, `/tmp/cdp.py`): `GET http://127.0.0.1:9222/json/list` (launch `--remote-debugging-port=9222 --remote-allow-origins=*`), then a RAW stdlib websocket for `Page.enable`, `Runtime.evaluate`, `Page.captureScreenshot`; decode the PNG in-guest with `zlib` + the five filter types. `captureScreenshot` is chromium's OWN compositor output, so it separates "chromium never rendered" from "X/selkies never captured it" -- **and it TIMES OUT when the compositor presents nothing, so `fromSurface:false` asks the renderer.** Never `--disable-dev-shm-usage` (shm moves to `/tmp`, where each process gets a COPY).
- **The client connect is what makes selkies fork.** On connect it applies a system DPI change: `INFO:ws:DPI changed from 96 to 120` -> `display_utils.py:1858` `_run_xfconf` -> `await subprocess.create_subprocess_exec("xfconf-query",...,"/Xft/DPI","-s","120")` -- blocks in `_communicate_or_kill` (source `/lsiopy/lib/python3.13/site-packages/selkies/display_utils.py`; selkies runs under `/lsiopy`, NOT system python3). Under host memory pressure selkies dies there. **The last log line before such a death is always `WARNING:display:Could not obtain XFCE session environment. Falling back to direct execution.`** -- permanent, because `/proc/<pid>/cmdline` is empty. **Rule: a selkies death whose last line is that WARNING is host starvation at the first selkies-side fork, not a litebox fork bug.**
- **XWD grab: field 11 is NOT the stride** -- `bytes_per_line` is field **12**, RGB masks **14/15/16**, pixels start at `len(raw) - w*h*bpp`, little-endian when `byte_order == 0`. **Every `blue=0.00%` from chrD19 and earlier is INVALID.** That `start` can be off by one byte, rotating the channels.
- **A file a fork child wrote is visible only to the shell that reaps it**: a headless `--screenshot` must run chromium in the FOREGROUND of its subshell with the analysing python after it in that SAME subshell (`chrdesk8.sh`). Blue PNG = compositor fine; white PNG = no frame.
