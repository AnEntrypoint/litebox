Fixed, newest first (mechanism per sha in the archive; each bullet keeps only the *rule*):
- `31ca26b` `MAX_INLINE_WAITERS` 32->128; the queue-full fallback no longer polls/logs per attempt (chrD14: 140MB `.err.log` in 9 min). **A waiter queue sized for one guest is not sized for one guest SESSION of 38 processes.**
- `1732ad9` a carried-pipe pump could outlive its child: `ForkPipeBridge::Source` blocked in `end.read()` with no deadline. A plain timeout cannot fix it, because `Option<usize>` collapsed "nothing yet" into EOF. Reads are now three-way `ForkPipeRead` (`litebox/src/platform/mod.rs:1549`), and the pump re-checks `process_has_exited` (`process_fork.rs:1530`) on every `Empty`.
- `463dc29` the "a parent's event loop stops when its spawned child exits" freeze. A `Source` pump forwarded bytes stalled 500ms in the parent's pipe -- but "stalled" only means the read has not happened YET, so it EMPTIED inherited read ends the guest still meant to read. libuv's GLOBAL SIGNAL LOCK is exactly that shape (one byte; `uv__signal_lock() == read(pipefd[0],&c,1)`), so one carried fork empties it and the next SIGCHLD blocks in `uv_run` for ever. Forwarding is now restricted to the carried end that is the child's stdin (`fd == 0`). **Never drain a pipe the guest holds for itself.**
- `5b7ff62` `ShimTransport::connect` drops `net_lock` before its `spin_loop` (a `match` kept the temporary guard alive, so the spin held a cross-process lock with no timeout).
- `42c6099` queued bytes reach smoltcp before `close(2)` defers them: the TX ring lives in the exiting process's own heap, so write-then-exit delivered nothing.
- `a1423ee` a carried "child writes" pipe is a local pipe + pump, so `write(2)` returns before the bytes reach the parent. HOLDING an end is not READING it (a `timeout`/`env`/`nohup`/`setpriv` wrapper keeps stdin open for its child) -- `pending_bytes` (FIONREAD) breaks that wait.
- `7d2a6a7` `SHARED_UNIX_CONN_CAPACITY` 1024->4096 (`litebox_shim_linux/src/syscalls/unix.rs:3726`) + every unadopted-carry discard releases the sender's slot hold: chromium renders with its OWN sandbox active.
- Older fixes (`067367b`, `19eab93`, `e608959` `chroot(2)`, `2bb71cb` `seccomp(2)`, `9412184`, `6beb669`, `d428acd`, `9014df7`, `3ee1ce7`/`bff1d0b`/`a61ed74`, `d383f90`/`d1dae93`): mechanism per sha in the archive. Standing rules from that range: `bb518ca` (any new per-child env var needs a remove after adoption); beware root-vs-child heap layout exposing shared-struct host pointers.

## The net_lock freeze (root-caused `16f3e76`, verified chrD7)

16+ processes parked `val=2` on one arena mutex whose `holder_pid` was ALIVE; cdb had that holder's net_worker blocked in `RawRwLock::read_contended`. CAUSE: `perform_network_interaction` (`litebox_shim_linux/src/lib.rs:1283`) holds the arena-resident `net_lock` across `internal_perform_platform_interaction` (`litebox/src/net/mod.rs:862`), which took the descriptor-table/entry locks BLOCKINGLY; `litebox::sync::RwLock` is writer-preferring (`litebox/src/sync/rwlock.rs:74-82`), so a QUEUED writer blocks a reader. FIX: net-worker maintenance is best effort (`try_descriptor_table_mut` + `drain_entries_full_covered_by_nowait` in `attempt_to_close_queued`; `try_descriptor_table` in `close_pending_sockets`/`drain_all_socket_channel_buffers`). **Rule: no path holding `net_lock` may block.**

## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole guest session). Refusal errno is API contract: EPERM lets callers degrade, EINVAL/ENOSYS fails them hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check (never `PrintWindow`/`CopyFromScreen`). Never time litebox with one host process per datapoint (a bare spawn costs 1.6-2.3s), and never subtract timestamps across a parent log and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A mutable table on the `SharedUnixAddrPresenceTable` pattern needs every write path mirrored to the shared side.
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`, `litebox_platform_windows_userland/src/lib.rs:13886`); carried: pipes/regular files/eventfds/pty/unix sockets; dropped: cloexec + pty fds. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6, `litebox_shim_linux/src/lib.rs:3908`) gates the spawn and fails open after 8s, because each child rebuilds the whole OCI rootfs in its own heap (~350MB-1.1GB). Slots are keyed by child host pid and freed at STARTUP-COMPLETE, not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it; unset it for the same-process path.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot on any task sharing that state roots all of them, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (the parent never resumes, process dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer the dedicated low-overhead targets over blanket module debug (`syscalls::file=debug` floods 50MB/s). Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env vars: `LITEBOX_PROCESS_FORK` (presence-checked), `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Dispatched subagents: Sonnet, not Opus (omit `model` or pass `model: "sonnet"`). Web search: Google, not DuckDuckGo; if Google is blocked or bot-detected fall back to camoufox, never to DDG.

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` (`litebox_shim_linux/src/syscalls/process.rs:4938`) spawns a host thread (`litebox-xproc-exit-notifier`, `litebox_platform_windows_userland/src/lib.rs:13658`) blocking on the child's INITIATING THREAD handle, then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. It waits on the THREAD, not the process, because extra OS threads can outlive the task.
- `sys_wait4` (`process.rs:3062`) re-polls every 15ms (`WAIT4_REPOLL_INTERVAL`, `:3081`) instead of trusting the notify, so it cannot hang on a lost wake; on reap it runs `import_cross_process_writable_layer` (`:3175`, a real tar read). `waitpid(-1)` only sees entries registered in THIS host process, so a grandchild is invisible -> ECHILD (`:3239`).
- SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it. `signalfd` is worse: nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`, `:218-225`), so a blocking read/epoll never wakes; `pidfd_open` (`inotify.rs:353`) does wake.
- The external fault watchdog (`run_external_fault_watchdog_child`, `process_fork.rs:5185`) polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. It is gated on the sticky event `Local\litebox-fault-armed-<pid>`, set only by the two VEH self-terminate paths (`lib.rs:2319`, `:2623`) -- and a NULL `OpenEventW` handle means ALWAYS ARMED (`:5247`/`:5251`). So it is a LATENT false positive (a healthy `Xvfb` blocked in `select()` qualifies), but NOT the observed killer.

## Cross-process shared memory and locks

`RawMutex` = a pointer-free wait queue + cross-process `Event`s with `holder_pid` dead-holder recovery (`bff1d0b`); waits chunk to `LIVENESS_CHECK_INTERVAL` (2s) so recovery can run. A 128MiB `shared_kernel_arena_alloc` (any mutex at/above `SHARED_KERNEL_HEAP_BASE` `0x7FF8_0000_0000`, `litebox_platform_windows_userland/src/lib.rs:11552`, is cross-process) backs `SharedArc<T>` (`GlobalState`, `Network`, pty/unix tables); `SharedArc::new` shares only `T`'s inline bytes (a `BTreeMap`'s nodes live on the private heap), so shared registries are fixed-slot atomic tables -- why `SharedUnixConnTable`'s slots moved to an arena slice (`unix.rs:4326`). `litebox::sync::RwLock` is writer-preferring -- a QUEUED writer blocks readers.

## Cross-process file visibility, identity, apt

- A file written by one host process is invisible to siblings until it exits (per-process writable layer). `syscalls/file_spill.rs` write-through-spills `SPILLED_PREFIXES` (`file_spill.rs:10-18`) to `%TEMP%\litebox-spill-<rootpid>\<slot>.bin` (1024 slots). Prefixes: apt's two dirs + five chromium paths. Extend the prefix LIST, not the mechanism -- do NOT "fix" a missing-file class by adding `/tmp/`; `%TEMP%\litebox-spill-*` is never cleaned up.
- Direction matters: a cross-process fork child receives the parent's exported writable layer AT SPAWN, while its own writes reach the parent only when it exits and `wait4` imports them (`litebox-forkwrite-*.tar`). So a fork carry of a fresh `/tmp` fd works and the same fd handed back over SCM_RIGHTS does not; `only_in_own_writable_layer` (`9412184`) is how the carry path tells those apart.
- The fs layers check permissions against the calling task's fsuid/fsgid (`litebox::fs::set_effective_identity`); root bypasses rwx bits. Anything walking the fs outside a syscall (export/import) must run inside `litebox::fs::with_root_identity` (`d428acd`).
- Fork children inherit cwd and full credentials (`task-state:` shim spec, fd `i32::MAX`); a child's deletions reach the parent as `.wh.` tar entries; only the newest `Source` pipe bridge of a read end drains.

Chromium must run NON-ROOT (`setpriv --reuid 911 --regid 911 --init-groups`) and `--user-data-dir` must be `chmod 777` when a root shell created it (else `SingletonLock: Permission denied` = exit 21).
- `seccomp(2)`/`prctl(PR_SET_SECCOMP)` are real: a classic-BPF interpreter (`syscalls/seccomp.rs`) on the raw syscall number at the top of `Task::do_syscall`; mode, `no_new_privs` and the filter stack live on `Process`. `SECCOMP_RET_TRAP` must RETURN THE SYSCALL NUMBER (`ad2659f`) and its 16-bit payload lands in `si_errno` (`067367b`).
