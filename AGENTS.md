## How to run and drive it

- No WSL, no hypervisor, ever - native Win32 exe. ALWAYS launch through `.wfgy/guest2.ps1` (a hand-written launch runs with fork OFF - `575f0e2`): `-Script <sh> -Run <name> -Secs <n> [-Publish h:g] [-ExtraEnv "K=V;K2=V2"] [-Exe]`. Its `Stop-Litebox` kills EVERY process under `target\release`; a bg "failed exit code 128" is that `taskkill`, NOT the run - `.wfgy/<run>.out` is authoritative. NEVER run a probe while another run is live.
- A REAPED BG SHELL LEAVES THE GUEST LIVE: chrF54's shell was reaped by the memory gate mid-churn and the guest kept forking - 55 litebox processes, free RAM 1714 MB, no shell left to harvest it. Sweeping recovered 3077 MB. Put `trap sweep EXIT TERM INT` in EVERY background run script; a `sweep` only at the top does not cover the reap. Run ONE ARM PER SHELL, or one reap costs both arms.

## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole session). Refusal errno is contract: EPERM degrades, EINVAL/ENOSYS fails hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check. Never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A `SharedUnixAddrPresenceTable`-shaped mutable table needs every write path mirrored to the shared side.
- **`(dev, ino)` is NOT a cross-process-stable file identity in litebox.** A fork child rebuilds its fs from the parent's exported writable layer, so `InodeAllocator` renumbers every runtime-created file: measured `dev` equal (1283027571) but `ino` 527 in the parent vs 1 in the child. **Any shared registry keyed on `(dev, ino)` cannot exclude across processes** -- so the pre-`f5d73ff` shared `BTreeMap` could never have done so either. Key on `(dev, path)` (`FilesState::lookup_fd_path`).
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`); carried: pipes/regular files/eventfds/pty/unix sockets; dropped: cloexec + pty fds; **NOT carried at all: shared-memory mappings (Open 1; `f2d67f8` did it and was reverted by `112cae4`)**. INET sockets ARE carried (`712611c`, branch `inetfork`): named by ENDPOINT, not by smoltcp slot index (`SocketHandle`'s index is private and the ordinal is not stable across the ~1s a child takes to boot); a carried connection/bound UDP socket is `borrowed`, so a child closing it (or exiting) cannot tear down the parent's end; a LISTENER is instead rebuilt locally, so two live listeners on one port race for the SYN -- litebox has no shared accept queue (real Linux delivers to either). `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6, `lib.rs:3931`) gates the spawn and fails open after 8s, because each child rebuilds the OCI rootfs in its own heap. Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it. The post-duplication clone site is SUPERSEDED (`process.rs:6206`) -- believe `try_cross_process_fork`'s log.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot roots every task sharing that state, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets over blanket module debug.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`, `LITEBOX_PROCESS_FORK_IGNORE_FDS`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`. ## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` (`process.rs:4994`) spawns a host thread (`platform/lib.rs:13842`) blocking on the child's INITIATING THREAD handle (extra OS threads can outlive the task), then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. `sys_wait4` (`process.rs:3067`) re-polls every 15ms instead of trusting the notify; on reap it runs `import_cross_process_writable_layer` (a real tar read). `waitpid(-1)` only sees entries registered in THIS host process -> ECHILD.
- SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it. `signalfd` never wakes -- nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`); `pidfd_open` (`inotify.rs:353`) does.
- The external fault watchdog (`process_fork.rs`) polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. Gated on the sticky event `Local\litebox-fault-armed-<pid>` (a NULL `OpenEventW` handle means ALWAYS ARMED); LATENT false positive.

- `litebox::sync::RwLock::try_read`/`try_write` FAIL when a writer is merely QUEUED (`sync/rwlock.rs`).
- The cross-process fork copy plan is GRANULE-widened (`GRANULE = 0x1_0000`; a group base must stay granule-aligned or Windows answers 87). NOTHING in `litebox/src/mm` zeroes a fresh page: the guarantee is `MEM_COMMIT`. `vma_layout()` zips positionally: filter ALL or NONE.

- A process's writes are invisible until it is REAPED. Carried: pipes/files/eventfds/pty/unix sockets + INET + `MAP_SHARED`; dropped: pty fds, non-INET cloexec fds; slots (6) gate the spawn, fail open after 8 s. `fork_carry` holds the child's end under the PARENT's pid; CONTROL: a long-lived child must make `recv` TIME OUT. `file_spill.rs`: extend `SPILLED_PREFIXES`, do NOT add `/tmp/`.
- Lazy file map: chunks >= 256 KiB are `PAGE_NOACCESS`, VEH-filled by OCI LAYER INDEX; `Some("")` = a real 0x00, `None` = the read faulted. Shared unix conn slots (4096) are counted by host-process liveness.
- Child exit: `waitpid(-1)` sees only children registered in THIS host process (ECHILD); SIGCHLD is dispatched only at `check_for_interrupt`/`prepare_to_run_guest`, so `pidfd_open` wakes and `signalfd` does not. Timestamps = per-process uptime; `tag=`/`dtag=` do NOT identify a host process. Census `local_port:state:remote_port` cannot prove a port is armed.
- `ps -eo pid,args` is INVALID for chromium's children; a DEAD fork child can stay listed in another process's `ps`.
