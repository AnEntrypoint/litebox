## Fixed, newest first (mechanism per sha in the archive; keep only the *rule*)

- `9f7c994` **A sized memfd is ONE store again** (`shmvis10`/`shmvis12`; probe `.wfgy/memfd1.sh` 28/28). `write(2)`/`read(2)` hit the in-mem file in the PER-PROCESS writable layer while `mmap(MAP_SHARED)` hit the named section, and `install_shm_file` (the fork/SCM_RIGHTS rebuild) opened only the section -- so `mmap` write then `read(2)` returned ZEROS and a fork child read zeros while the parent read its own. Fixed by making the OBJECT the store and the file its mirror (`resize_memfd_shared_backing` seeds a new object from the file, `memfd_write_through`/`memfd_read_through`, `try_memfd_mmap` no longer copies file->object). **Rule: the shared object is the store; the in-mem file is only `fstat`'s size plus the fd position.**
- `575f0e2` **An fd with no name AND no shared object yet (a `memfd_create` fd before its first `ftruncate`) is carried as a byte snapshot instead of refusing the fork**. Before (`shmvis3`): every child forked while the parent held a memfd died `status=11` before one instruction, while `shmvis4`/`5` (memfd closed / sized / `MFD_CLOEXEC`) reached `status=0` -- the log read `clone: cross-process fork() not eligible ... uncarriable=1 kinds=["file"]`, silently DOWNGRADING `fork()` onto the RELOCATING fallback that faults the child (`Exception(14) cr2=0xa2c5a8`, `rip` off by 0x1860000). After (`shmvis3d`): all `status=0`. **Rule: an uncarriable fd returns NO errno -- it silently drops the fork off the cross-process path.** `LITEBOX_PROCESS_FORK_IGNORE_FDS` (`process.rs:4074`) = "carry what can be carried, lose the rest".
- `f7d0f79` SysV shm attachments drop when a process exits (`detach_sysv_shm_on_process_exit`, `mm.rs:533`): an MIT-SHM client dying without `shmdt` no longer leaks a slot (`shm2.sh` 8/200 -> 200/200).
- `f5d73ff` **flock(2) registry moved off byte-shared `GlobalState` onto `GlobalStateHandle`** (`lib.rs:3605`): a fork child inherits inline bytes only, so its `BTreeMap` nodes and `Pollee` observers were garbage -> `btree/node.rs:1232: range end index 65529 out of range for slice of length 11` in `do_flock`, child rc=137, zero output. **The panic correlated with LAUNCH ORDINAL, so every "X kills chromium" A/B in that window measured the ordinal, not the variable.** Per-process is right here -- unlike `drm`/`evdev` (Open 4).
- `b6e1142`+`1503276` SysV shm segments live until `shmctl(RMID)`: backing store is a real file (`<spill>/sysvshm/<name>.bin`) made at `shmget`, unlinked at RMID/last detach. Traps: open it with `FILE_GENERIC_EXECUTE` (a section's protection ceiling comes from its file handle's rights); and `win32_err=5` = VIEW LONGER THAN SECTION (grow the OBJECT).
- `31ca26b` `MAX_INLINE_WAITERS` 32->128 (`platform/lib.rs:6671`); the queue-full fallback no longer polls/logs per attempt. **A waiter queue sized for one guest is not sized for a 38-process session.**
- `1732ad9` a carried-pipe pump could outlive its child (`ForkPipeBridge::Source` blocked in `end.read()`); `Option<usize>` collapsed "nothing yet" into EOF. Reads are three-way `ForkPipeRead` (`litebox/src/platform/mod.rs:1549`); the pump re-checks `process_has_exited` on `Empty`.
- `463dc29` "a parent's event loop stops when its spawned child exits": a `Source` pump forwarded bytes "stalled 500ms", but stalled only means not yet read, so it EMPTIED read ends the guest still wanted -- libuv's GLOBAL SIGNAL LOCK is that shape (`uv__signal_lock() == read(pipefd[0],&c,1)`), so one carried fork empties it and the next SIGCHLD blocks in `uv_run` for ever. Forwarding is now only for the carried end that is the child's stdin (`fd == 0`). **Never drain a pipe the guest holds for itself.**
- `5b7ff62` `ShimTransport::connect` drops `net_lock` before its `spin_loop`. `42c6099` queued bytes reach smoltcp before `close(2)` defers them.
- `a1423ee` a carried "child writes" pipe is a local pipe + pump, so `write(2)` returns before bytes reach the parent. HOLDING an end is not READING it (`timeout`/`env`/`nohup`/`setpriv` keep stdin open for their child) -- `pending_bytes` (FIONREAD) breaks that wait.
- `7d2a6a7` `SHARED_UNIX_CONN_CAPACITY` 1024->4096 (`unix.rs:3726`) + every unadopted-carry discard releases the sender's slot hold: chromium renders with its OWN sandbox active.
- `16f3e76` **Rule: no path holding `net_lock` may block** -- it held the arena-resident `net_lock` across `internal_perform_platform_interaction` (`litebox/src/net/mod.rs:862`), which took descriptor locks BLOCKINGLY while `litebox::sync::RwLock` is writer-preferring.

## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole guest session). Refusal errno is API contract: EPERM lets callers degrade, EINVAL/ENOSYS fails them hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check (never `PrintWindow`/`CopyFromScreen`). Never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A mutable table on the `SharedUnixAddrPresenceTable` pattern needs every write path mirrored to the shared side.
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`, `platform/lib.rs`); carried: pipes/regular files/eventfds/pty/unix sockets; dropped: cloexec + pty fds. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6, `lib.rs:3931`) gates the spawn and fails open after 8s, because each child rebuilds the OCI rootfs in its own heap. Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it. The post-duplication clone site is SUPERSEDED (`process.rs:6206`) -- believe `try_cross_process_fork`'s log.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot roots every task sharing that state, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets over blanket module debug. Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`, `LITEBOX_PROCESS_FORK_IGNORE_FDS`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Dispatched subagents: Sonnet, not Opus. Web search: Google, not DuckDuckGo; if blocked, camoufox; never DDG.

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` (`process.rs:4994`) spawns a host thread (`platform/lib.rs:13842`) blocking on the child's INITIATING THREAD handle (not the process: extra OS threads can outlive the task), then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. `sys_wait4` (`process.rs:3067`) re-polls every 15ms instead of trusting the notify; on reap it runs `import_cross_process_writable_layer` (a real tar read). `waitpid(-1)` only sees entries registered in THIS host process -> ECHILD.
- SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it. `signalfd` never wakes -- nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`); `pidfd_open` (`inotify.rs:353`) does.
- The external fault watchdog (`process_fork.rs`) polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. Gated on the sticky event `Local\litebox-fault-armed-<pid>` (a NULL `OpenEventW` handle means ALWAYS ARMED); LATENT false positive.

## Other subsystems (merged, not re-verified this pass)

- **Linux runner (`litebox_runner_linux_userland`):** cloud sessions boot `webtop:debian-xfce` (`--initial-files rootfs.tar --rewrite-syscalls --uid 0 --gid 0 --pid1 --tun-device-name tun0 ... /bin/sh /init`) into s6, Xvfb, XFCE, nginx, pulseaudio, dbus, Selkies; host browser at `http://10.0.0.2:3000` (TUN, host 10.0.0.1). Native fork (`has_native_fork()==true`): shared state must live in the arena; the thread-based fork corrupts guest memory on Linux.
- **Shared memory and locks:** `RawMutex` = a pointer-free wait queue + cross-process `Event`s with `holder_pid` dead-holder recovery (`bff1d0b`), chunking waits to `LIVENESS_CHECK_INTERVAL` (2s). A 128MiB `shared_kernel_arena_alloc` (anything at/above `SHARED_KERNEL_HEAP_BASE` `0x7FF8_0000_0000`, `platform/lib.rs`) backs `SharedArc<T>`, which shares only `T`'s inline bytes -- so shared registries are fixed-slot atomic tables (`SharedUnixConnTable`'s arena slice, `unix.rs:4326`).
- **File visibility:** a file one host process wrote is invisible to siblings until it exits. `file_spill.rs` write-through-spills `SPILLED_PREFIXES` (`file_spill.rs:10-18`) to `%TEMP%\litebox-spill-<rootpid>\<slot>.bin`; extend the prefix LIST, not the mechanism -- do NOT add `/tmp/`. Direction matters: a fork child gets the parent's exported writable layer AT SPAWN, and its own writes reach the parent only when it exits and `wait4` imports them -- so a fork carry of a fresh `/tmp` fd works and the same fd over SCM_RIGHTS does not (`only_in_own_writable_layer`, `9412184`). Fs permissions follow the calling task's fsuid/fsgid (`set_effective_identity`); root bypasses rwx bits; anything walking the fs outside a syscall must run inside `with_root_identity` (`d428acd`).
- **OCI:** `litebox_packager --oci-image <ref> --output <tar>` pulls, merges and rewrites every ELF; the runner does the same in memory (`.litebox-cache/`, keyed by `REWRITER_CACHE_VERSION`). `linuxserver/webtop:debian-xfce` and `ubuntu-xfce` ship XFCE.

## Guest stack: chromium + selkies

MILESTONE (chr21/22): `.wfgy/guest2.ps1 -Script .wfgy/chr15.sh -Run chr21` (webtop, no `--no-sandbox`) -> `CHROME_PIPELINE_DONE rc=0`; 6x `Activated seccomp-bpf`, ZERO `No usable sandbox!`.
- **TWO chromium failure modes -- do not merge them.** (a) `Crashing due to FD ownership violation:` + `zygote_host_impl_linux.cc:129] No usable sandbox!` = the `CanCreateProcessInNewUserNS()` probe. (b) rc=133 (SIGTRAP) with NO sandbox line = crashpad/HOME (chrD31's `CHROMIUM_A_EXIT rc=133`).
- **A `HOME` chromium shares with anything root ran kills it**: a root-run app makes `$HOME/.config` 0755 root, so uid 911 gets `stat $HOME/.config/chromium/Crash Reports: Permission denied (13)`; crashpad mkdirs only its LAST component, so a missing chain is ENOENT (2). Fix: `mkdir -p $HOME/.config/chromium; chmod -R 777; chown -R 911:911` on a HOME nothing else touched -- `chmod 777` on a SHARED HOME is NOT enough.
- NON-ROOT (`setpriv --reuid 911 --regid 911 --init-groups`); `--user-data-dir` `chmod 777` when a root shell created it (else `SingletonLock: Permission denied`, exit 21). `HOME=/tmp/cuhome` exits 0 (`.wfgy/cpad1.sh`); `--crash-dumps-dir` does not exist in Debian's build.
- `seccomp(2)` is real: a classic-BPF interpreter (`syscalls/seccomp.rs`) on the raw syscall number at the top of `Task::do_syscall`; `SECCOMP_RET_TRAP` must RETURN the syscall number (`ad2659f`), payload in `si_errno` (`067367b`).
- Still open: (1) the launcher thread SERIALISES cross-process spawns, so children hit the 15s "no connection" self-termination; (2) `--single-process` dies on a CHECK in `RenderProcessHostImpl`; (3) `Vmem::duplicate` skips `VM_OWN_FORK_PADDING` (same-process fork); (4) ~1/run `rebuilding a carried SCM_RIGHTS fd failed errno=ENOENT`; (5) GWP-ASan `MapRegion` EEXIST.
- **XWD grab: field 11 is NOT the stride.** `bytes_per_line` is field **12**, RGB masks **14/15/16**, pixels start at `len(raw) - w*h*bpp`, pixel words little-endian when `byte_order == 0`. Correct reader: `/tmp/xwd.py` in `.wfgy/chrdesk16.sh`-`19.sh`. **Every `blue=0.00%` from chrD19 and earlier is INVALID.**
- **A file a fork child wrote is visible only to the shell that reaps it**: a headless `--screenshot` must run chromium in the FOREGROUND of its subshell with the analysing python after it in that SAME subshell (`.wfgy/chrdesk8.sh`).
- Never `--enable-logging=stderr --v=1` in a long run (chrD13 stopped painting while the stream held 32-37fps). Windowed recipe: `xfconf-query -c xfwm4 -p /general/use_compositing -s false`, `xsetroot -solid "#305070"`.
- Host-browser frames: CDP `take_screenshot` CANNOT SEE A `<video>` (two shots 2 min apart at 40fps were BYTE-IDENTICAL, mean RGB (0,0,0)); use JS `drawImage(video)` + `toDataURL('image/png')`, decoded host-side (`.wfgy/chrD8_frame.png`). A black screenshot is not evidence of a broken stream.
- xfce4-session takes ~120s to register its WM (`WM_POLL n=24`); until then `xprop -root _NET_SUPPORTING_WM_CHECK` answers "not found" and the stream is a legitimately black root.
- SELKIES 2.0.0 BINDS 8080, NOT 8081; `CUSTOM_WS_PORT` is a 1.x name it ignores, so `--port=8081` must be explicit. It ENABLES BASIC AUTH BY DEFAULT and, with no password set, STOPS ITS OWN SERVER -- always `--enable-basic-auth=false` or set `PASSWORD`.
- **A host browser reaches a guest SERVER only through `-p/--publish h:g`**: the runner's network is OUTBOUND NAT only (why chrD23 got `ERR_CONNECTION_REFUSED` while the guest's own `curl` read `code=200`).
- **selkies' capture REQUIRES MIT-SHM at the X server**: pixelflux's X11 path is NvFBC -> DRI3 -> XShm and `run_shm_capture` HARD-FAILS on `shm_query_version` (`pixelflux/src/x11/mod.rs:1097-1138`, `:1198-1201`) -- no XGetImage fallback, no flag. On failure the client connects then hits `ERROR:ws:FATAL: Initial reconfiguration completed, but video pipeline did not start` (`src/selkies/websockets_mode.py:3936`); the real diagnosis is the line above it, `Failed to start capture for 'primary': <e>` (`:5685`). Knobs: `PIXELFLUX_DEBUG=1` (the `[X11] Res:` lines are `debug!`-gated) and `--use-cpu true`. After a FATAL, `video_active` stays set and `VIDEO_STOPPED` goes out, so re-pressing `Play Stream` retries.
- A log selkies writes under `/tmp/` is INVISIBLE to the launching shell -- pipe it: `( selkies --debug 2>&1 | sed 's/^/[selk] /' ) &`. A/B on ONE port is useless (`kill -9` on a wedged cross-process child does not reap it -> `Address already in use`).
