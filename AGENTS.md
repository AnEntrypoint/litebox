## Fixed, newest first (mechanism per sha in `docs/AGENTS_ARCHIVE_*`; keep only the RULE)

- `6c63d41` **An INET socket crosses a cross-process fork** (`Network::fork_carry_spec`/`fork_adopt`, `inet:<cloexec>|<v6>|<nonblock>|<spec>`). It used to hit the `None =>` arm, so ONE TCP/UDP fd made the whole fork "not eligible" -> relocating fallback -> `Exception(14) error_code=0x7` before the child's first instruction. Named by ENDPOINTS (`T,lip,lport,rip,rport` / `L,...` / `U,...` / `u`), never by smoltcp slot index (unstable across the ~1s a child takes to boot). A carried connection or bound UDP socket is `borrowed`: `close_handle` releases only that reference -- no smoltcp close/abort, no port deallocation -- because those would tear down the parent's socket; a listener is rebuilt locally (`refill_to_backlog`). **An unnamable INET fd (Icmp/Raw, bound-but-unconnected TCP) is DROPPED (EBADF in the child), never allowed to poison the fork.** chrD76: grey -> blue at t=30.
- `bfc33f7` (branch `shmfork2`, NOT merged) **an unplaceable page-granular hole must not kill the host process.** `reserve_and_commit` rounds MEM_RESERVE out to the 64 KiB granularity, so a merely page-aligned range whose granule holds a live neighbour is refused with 487: **any page-granular allocation poisons its granule for the process's life**, and under `e41cafa9` a fork child is full of them -- the first ordinary guest `mmap()` in one died on `process_memory_range_by_regions`' `assert!` (`platform/lib.rs:8366`), losing all three chromium launches (chrD72 pids 74/114/154, `0x7feffeced000-0x7fefff4e3000`). **Premise correction: that range is ~34 GB ABOVE the arena base `0x7ff800000000` and chrD72 has ZERO carry-failure lines -- never an arena-region bug.** Fix: a `Hint` asks for a neighbourhood, so RELOCATE it; `NoReplace` -> AddressInUse, `Replace` -> OutOfMemory.
- `e41cafa9` **A cross-process fork child SHARES `MAP_SHARED` with its parent** (branch `shmfork`, NOT merged; `112cae4` reverted `f2d67f8`: chrD62 rc=133, chrD63 no window, carry-free control chrD61 ZERO exceptions). Carry = reserve a placeholder in the child, `MapViewOfFile3` the parent's section into it (`MEM_REPLACE_PLACEHOLDER`). Killer trap: **validate every segment BEFORE reserving the group placeholder** -- checking after leaves a live placeholder over the span the byte-copy fallback re-reserves -> 487 -> `spawn/resume failed` -> thread-based fork -> `Exception(14) error_code=0x7`. Also: `VirtualFreeEx(MEM_RELEASE|MEM_PRESERVE_PLACEHOLDER)` over a whole placeholder returns 487; the alignment check is `PAGE_SIZE`, not the granularity. **The synthetic probes never exercise a FAILED carry**, so degradation is MEASURED via `LITEBOX_DIAG_FORK_SHARED_FORCE_FAIL=1` (shmfork1/2 reproduce the pre-fix baseline). - `f260226` **Cross-process `flock(2)` EXCLUSION works** (branch `flockx`): a fork child's `LOCK_EX|LOCK_NB` on a file the parent holds is `EWOULDBLOCK` (11) -- it used to SUCCEED -- and its blocking `LOCK_EX` returns when the parent unlocks (3.9s vs an unlock at t=4s). `SharedFlockTable` (`file.rs`, 128 slots x 32 holders, pointer-free atomics, 25ms chunks, dead-pid reclaim, `wake_all`); per-process `FlockFile` kept as degradation. **Keyed on `(dev, path)`, NOT `(dev, ino)`**; two hard links no longer contend, delete-and-recreate does. ## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole session). Refusal errno is contract: EPERM degrades, EINVAL/ENOSYS fails hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check. Never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A `SharedUnixAddrPresenceTable`-shaped mutable table needs every write path mirrored to the shared side.
- **`(dev, ino)` is NOT a cross-process-stable file identity in litebox.** A fork child rebuilds its fs from the parent's exported writable layer, so `InodeAllocator` renumbers every runtime-created file: measured `dev` equal (1283027571) but `ino` 527 in the parent vs 1 in the child. **Any shared registry keyed on `(dev, ino)` cannot exclude across processes.** Key on `(dev, path)` (`FilesState::lookup_fd_path`).
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`); carried: pipes/regular files/eventfds/pty/unix sockets/**INET**; dropped: cloexec + pty fds; **NOT carried at all: shared-memory mappings (Open 1)**. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6) gates the spawn and fails open after 8s, because each child rebuilds the OCI rootfs in its own heap. Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it. The post-duplication clone site is SUPERSEDED -- believe `try_cross_process_fork`'s log.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot roots every task sharing that state, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets over blanket module debug. Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`, `LITEBOX_PROCESS_FORK_IGNORE_FDS`, `LITEBOX_DIAG_FORK_SHARED_FORCE_FAIL`, `LITEBOX_FLOCK_SHARED_OFF`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Dispatched subagents: Sonnet, not Opus. Web search: Google, not DuckDuckGo; if blocked, camoufox; never DDG.

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` spawns a host thread blocking on the child's INITIATING THREAD handle (extra OS threads can outlive the task), then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. `sys_wait4` re-polls every 15ms instead of trusting the notify; on reap it runs `import_cross_process_writable_layer` (a real tar read). `waitpid(-1)` only sees entries registered in THIS host process -> ECHILD. **SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it**; `signalfd` never wakes -- nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`); `pidfd_open` (`inotify.rs:353`) does.
- The external fault watchdog polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. Gated on the sticky event `Local\litebox-fault-armed-<pid>` (a NULL `OpenEventW` handle means ALWAYS ARMED); LATENT false positive.

## Guest stack: chromium + selkies

- **TWO chromium failure modes -- do not merge them.** (a) `Crashing due to FD ownership violation:` + `zygote_host_impl_linux.cc:129] No usable sandbox!` = the `CanCreateProcessInNewUserNS()` probe. (b) rc=133 (SIGTRAP) with NO sandbox line = crashpad/HOME.
- **A `HOME` chromium shares with anything root ran kills it**: a root-run app makes `$HOME/.config` 0755 root, so uid 911 gets `stat $HOME/.config/chromium/Crash Reports: Permission denied (13)`; crashpad mkdirs only its LAST component, so a missing chain is ENOENT (2). Fix: `mkdir -p $HOME/.config/chromium; chmod -R 777; chown -R 911:911` on a HOME nothing else touched -- `chmod 777` on a SHARED HOME is NOT enough. chrD61's `PREP_LS` prints the chain before launch.
- NON-ROOT (`setpriv --reuid 911 --regid 911 --init-groups`); `--user-data-dir` `chmod 777` when a root shell created it (else `SingletonLock: Permission denied`, exit 21). `HOME=/tmp/cuhome` exits 0 (`.wfgy/cpad1.sh`); `--crash-dumps-dir` does not exist in Debian's build.
- `seccomp(2)` is real: `syscalls/seccomp.rs` interprets classic BPF at the top of `Task::do_syscall`; `SECCOMP_RET_TRAP` must RETURN the syscall number (`ad2659f`), payload in `si_errno` (`067367b`).

- **CDP from inside the guest is the decisive chromium probe** (`.wfgy/chrdesk38.sh`, `/tmp/cdp.py`): `GET http://127.0.0.1:9222/json/list` (launch `--remote-debugging-port=9222 --remote-allow-origins=*`), then a RAW websocket (stdlib only -- no websocket-client in the image) for `Page.enable`, `Runtime.evaluate`, `Page.captureScreenshot`; decode the PNG in-guest with `zlib` + the five filter types. `captureScreenshot` is chromium's OWN compositor output, so it separates "chromium never rendered" from "X/selkies never captured it" -- **and it TIMES OUT when the compositor presents nothing, so `fromSurface:false` asks the renderer.** Never `--disable-dev-shm-usage` (shm moves to `/tmp`, where each process gets a COPY -- `file_spill.rs:10-18`).
