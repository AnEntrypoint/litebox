## Fixed, newest first (mechanism per sha in the archive; keep only the *rule*)

- `9f7c994` **A sized memfd is ONE store again** (`shmvis10`/`shmvis12`). `write(2)`/`read(2)` hit the in-mem file in the PER-PROCESS writable layer while `mmap(MAP_SHARED)` hit the named section `ftruncate` created, and the fork/SCM_RIGHTS rebuild (`install_shm_file`) opened only the section -- so `mmap` write then `read(2)` returned ZEROS and a fork child read a zeroed buffer while the parent still read its own. Fixed by making the OBJECT the store and the file its mirror: `resize_memfd_shared_backing` seeds a fresh object from the file (so a pre-`ftruncate` `write(2)` survives), `memfd_write_through` mirrors every file write into it, `memfd_read_through` answers `read(2)`/`pread(2)` from it, and `try_memfd_mmap` no longer copies the file over it (that sync was right while the file was a peer store; it then only destroyed live content -- a parent that had never mapped its memfd wiped everything its fork child had just written). **Rule: for a memfd, the shared object is the store and the in-mem file is only `fstat`'s size plus the fd position.** Probe `.wfgy/memfd1.sh` (28/28).
- `575f0e2` **An fd with no name AND no shared object yet (a `memfd_create` fd before its first `ftruncate`) is carried as a byte snapshot instead of refusing the fork** (`snapshot_carriable_file_for_raw_fd`/`install_snapshot_at_fd`). Before (`shmvis3`): every child forked while the parent held a memfd died `status=11` before one instruction; `shmvis4`/`5` (memfd closed / sized / `MFD_CLOEXEC`) reached `status=0`, so the memfd was never the killer -- the log read `clone: cross-process fork() not eligible ... uncarriable=1 kinds=["file"]`, which silently DOWNGRADED `fork()` onto the thread-based RELOCATING fallback, and THAT faults the child (`Exception(14) cr2=0xa2c5a8`, `rip` off by the 0x1860000 base). After (`shmvis3d`): all `status=0`. **Rule: an uncarriable fd returns NO errno -- it silently drops the fork off the cross-process path.** `LITEBOX_PROCESS_FORK_IGNORE_FDS` (`process.rs:4074`) = "carry what can be carried, lose the rest"; measurement only.
- `f7d0f79` SysV shm attachments drop when a process exits (`detach_sysv_shm_on_process_exit`, `mm.rs:533`): an MIT-SHM client dying without `shmdt` no longer leaks a slot (`shm2.sh` 8/200 -> 200/200).
- `f5d73ff` **flock(2) registry moved off byte-shared `GlobalState` onto `GlobalStateHandle`** (`lib.rs:3605`; "NO field" note `:4210`). A fork child inherits inline bytes only, so the `BTreeMap`'s nodes and each `FlockFile`'s `Pollee` observers were garbage -> `btree/node.rs:1232: range end index 65529 out of range for slice of length 11` in `do_flock`, child rc=137 with ZERO output. **The panic correlated with LAUNCH ORDINAL, so every "X kills chromium" A/B in that window measured the ordinal, not the variable.** Per-process is right here -- unlike `drm`/`evdev` (Open 4).
- `b6e1142`+`1503276` SysV shm segments live until `shmctl(RMID)`: backing store is a real file (`<spill>/sysvshm/<name>.bin`) made at `shmget`, unlinked at RMID/last detach. Traps: open it with `FILE_GENERIC_EXECUTE` (a section's protection CEILING comes from its file handle's rights and `map_shared_memory` maps every view READ|WRITE|EXEC, so without it every `MapViewOfFile3` answers `ERROR_ACCESS_DENIED`); and `win32_err=5` means VIEW LONGER THAN SECTION -- grow the OBJECT, do not map a second view.
- `31ca26b` `MAX_INLINE_WAITERS` 32->128 (`platform/lib.rs:6671`); the queue-full fallback no longer polls/logs per attempt. **A waiter queue sized for one guest is not sized for a 38-process session.**
- `1732ad9` a carried-pipe pump could outlive its child (`ForkPipeBridge::Source` blocked in `end.read()`); `Option<usize>` collapsed "nothing yet" into EOF, so a timeout cannot fix it. Reads are three-way `ForkPipeRead` (`litebox/src/platform/mod.rs:1549`); the pump re-checks `process_has_exited` on every `Empty`.

## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole guest session). Refusal errno is API contract: EPERM lets callers degrade, EINVAL/ENOSYS fails them hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check (never `PrintWindow`/`CopyFromScreen`). Never time litebox with one host process per datapoint (a bare spawn costs 1.6-2.3s), and never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A mutable table on the `SharedUnixAddrPresenceTable` pattern needs every write path mirrored to the shared side.
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`, `platform/lib.rs`); carried: pipes/regular files/eventfds/pty/unix sockets; dropped: cloexec + pty fds. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6, `lib.rs:3931`) gates the spawn and fails open after 8s, because each child rebuilds the whole OCI rootfs in its own heap (~350MB-1.1GB). Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it. The post-duplication clone site is SUPERSEDED and only `debug!`s now (`process.rs:6206-6239`) -- believe the pre-duplication `try_cross_process_fork` log, the site that actually carries pipes/files/eventfds.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot on any task sharing that state roots all of them, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (parent never resumes, dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets over blanket module debug. Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`, `LITEBOX_PROCESS_FORK_IGNORE_FDS`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Dispatched subagents: Sonnet, not Opus. Web search: Google, not DuckDuckGo; if blocked, camoufox; never DDG.

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` (`process.rs:4994`) spawns a host thread (`platform/lib.rs:13842`) blocking on the child's INITIATING THREAD handle, then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. It waits on the THREAD because extra OS threads can outlive the task.
- `sys_wait4` (`process.rs:3067`) re-polls every 15ms instead of trusting the notify; on reap it runs `import_cross_process_writable_layer` (a real tar read). `waitpid(-1)` only sees entries registered in THIS host process, so a grandchild is invisible -> ECHILD.
- SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it. `signalfd` never wakes: nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`); `pidfd_open` (`inotify.rs:353`) does.
- The external fault watchdog (`process_fork.rs`) polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. Gated on the sticky event `Local\litebox-fault-armed-<pid>`, set only by the two VEH self-terminate paths -- a NULL `OpenEventW` handle means ALWAYS ARMED. LATENT false positive (a healthy `Xvfb` in `select()` qualifies), not the observed killer.

## Other subsystems (merged, not re-verified this pass)

- **Linux runner (`litebox_runner_linux_userland`):** cloud sessions boot `webtop:debian-xfce` (`--initial-files rootfs.tar --rewrite-syscalls --uid 0 --gid 0 --pid1 --tun-device-name tun0 ... /bin/sh /init`) into s6, Xvfb, XFCE, nginx, pulseaudio, dbus, Selkies; host browser at `http://10.0.0.2:3000` (TUN, host 10.0.0.1). Native fork (`has_native_fork()==true`): a child COW-copies every private kernel structure, so shared state must live in the arena; the thread-based fork corrupts guest memory on Linux.
- **Cross-process shared memory and locks:** `RawMutex` = a pointer-free wait queue + cross-process `Event`s with `holder_pid` dead-holder recovery (`bff1d0b`); waits chunk to `LIVENESS_CHECK_INTERVAL` (2s). A 128MiB `shared_kernel_arena_alloc` (anything at/above `SHARED_KERNEL_HEAP_BASE` `0x7FF8_0000_0000`, `platform/lib.rs`) backs `SharedArc<T>`; `SharedArc::new` shares only `T`'s inline bytes (a `BTreeMap`'s nodes live on the private heap), so shared registries are fixed-slot atomic tables -- why `SharedUnixConnTable`'s slots moved to an arena slice (`unix.rs:4326`). `litebox::sync::RwLock` is writer-preferring -- a QUEUED writer blocks readers.
- **Cross-process file visibility:** a file written by one host process is invisible to siblings until it exits (per-process writable layer). `file_spill.rs` write-through-spills `SPILLED_PREFIXES` (`file_spill.rs:10-18`) to `%TEMP%\litebox-spill-<rootpid>\<slot>.bin` (1024 slots): apt's two dirs + five chromium paths. Extend the prefix LIST, not the mechanism -- do NOT add `/tmp/`; the spill dir is never cleaned up. Direction matters: a fork child receives the parent's exported writable layer AT SPAWN, and its own writes reach the parent only when it exits and `wait4` imports them (`litebox-forkwrite-*.tar`) -- so a fork carry of a fresh `/tmp` fd works and the same fd over SCM_RIGHTS does not (`only_in_own_writable_layer`, `9412184`). Fs layers check permissions against the calling task's fsuid/fsgid (`litebox::fs::set_effective_identity`); root bypasses rwx bits; anything walking the fs outside a syscall must run inside `litebox::fs::with_root_identity` (`d428acd`). Children inherit cwd and full credentials; deletions reach the parent as `.wh.` tar entries; only the newest `Source` pipe bridge of a read end drains.
- **Containers and OCI:** `litebox_packager --oci-image <ref> --output <tar>` pulls, merges and rewrites every ELF; the runner does the same in memory (`.litebox-cache/`, keyed by `REWRITER_CACHE_VERSION`). `linuxserver/webtop:debian-xfce` and `ubuntu-xfce` ship XFCE; never trust a tag name.
