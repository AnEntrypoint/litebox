## How to run and drive it (prose: `docs/HARNESS-LESSONS.md`)

- **No WSL, no hypervisor, ever.** Native Win32 exe. **ALWAYS launch through `.wfgy/guest2.ps1`** (a hand-written launch runs with fork OFF - `575f0e2`): `-Script <sh> -Run <name> -Secs <n> [-Publish h:g] [-ExtraEnv "K=V;K2=V2"] [-Exe]`. Its `Stop-Litebox` kills EVERY process under `target\release`, so B while A is live kills A; a background "failed exit code 128" is that `taskkill`, NOT the run - `.wfgy/<run>.out` is authoritative. **NEVER run a probe while another run is live.**

- **A HOST-SIDE HELPER CANNOT POLL `.wfgy/<run>.out`** (the runner holds it EXCLUSIVELY; `ReadAllText` throws, a swallowed catch looks alive doing nothing). bash `grep -a` DOES read a runner-held `.out`/`.err`. Use a FIXED delay (**chrF30 reached HOLD at ~70 s - probe from ~100 s**) and let the helper's own rc/bytes be its proof. **STREAM a crashing guest process's stderr - never redirect it to a file** (a fork child's file writes are invisible until it exits).

- **HOST RESOURCE GATE (stated only here)**: a background shell DIES AT ITS 30 MIN CAP (keep `-Secs` <=1500) and is REAPED WHEN HOST MEMORY IS CRITICALLY LOW, INCLUDING a `cargo build` (killed at ~1.3 GB free) - never re-read a killed build as a compile error. **A gate is a SNAPSHOT, not a reservation**; a short slice (~5 arms / ~7 min) survives a swing that reaps a 23-min run. **A REAPED SHELL IS NOT A DEAD GUEST.** See also NEVER-KILL below.

## Standing lessons (FULL TEXT: `docs/HARNESS-LESSONS.md` - read it; only the subset needed on every run is here)

- **NEVER KILL: the two stuck `python.exe gcloud.py` deploy loops (the user's), gm's browser (2.2 GB PER INSTANCE) + its plugkit build, the `queue.mjs` chrome storm, `bun`. Check host RAM FIRST - when free RAM is short there is nothing safe to reclaim, wait.**

- **`litebox::sync::RwLock::try_read`/`try_write` FAIL WHEN A WRITER IS MERELY QUEUED** (`litebox/src/sync/rwlock.rs`): one parked `descriptor_table_mut()` makes every `try_descriptor_table()` fail forever; recovery needs the owner thread DEAD.

- **THE CROSS-PROCESS FORK'S COPY PLAN IS GRANULE-WIDENED AND MERGED** (`process.rs`: `GRANULE = 0x1_0000`; a group base MUST stay granule-aligned or Windows answers 87). **NOTHING IN `litebox/src/mm` ZEROES A FRESH PAGE** - the guarantee is Windows `MEM_COMMIT`, which does not re-zero an already-committed page. **`vma_layout()` zips `ranges`/`flags`/`executable`/`is_file_backed` POSITIONALLY - filter ALL or NONE.**

- **A GUEST PACKET TO `127.0.0.0/8` OR TO `GUEST_IP_ADDR` IS LOOPED IN-PROCESS** (`phy.rs:166`): a guest's `127.0.0.1:<port>` NEVER reaches the host's published listener; **`data_granted` = CAPACITY granted, `data_used` = slots in use**.

- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check. Never subtract timestamps across a parent and a fork-child log.

- **A `TypedFd` index is valid only against the `Descriptors` that inserted it, and only for its own subsystem.** **No per-tick sweep may DROP another process's object.** **A backlog slot of a listening port is reachable by NOTHING but `accept`.** **`(dev,ino)` is cross-process-stable for IMAGE files ONLY** - key shared registries on `(dev,path)`.

- **A process's writes are invisible to everyone until it is REAPED, not when it closes**; a fork child's writes reach the parent only on `wait4`. Carried: pipes/files/eventfds/pty/unix sockets + INET + `MAP_SHARED`; dropped: pty fds, non-INET cloexec fds; slots (6) gate the spawn, fail open after 8 s.

- Logs: verbosity from `LITEBOX_LOG`, not `RUST_LOG`; **`debug!` fields take `&str`, not an owned `String`**; **timestamps are PER-PROCESS UPTIME, `.err` lines carry ANSI escapes**; **`tag=`/`dtag=` DO NOT identify a host process**.
