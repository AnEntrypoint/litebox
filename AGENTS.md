## Fixed, newest first (mechanism per sha in the archive; keep only the *rule*)

- `6a472b5` **`shmat` on a segment that was `IPC_RMID`'d but still has an attach SUCCEEDS** (`mm.rs`: `seg.removed && seg.attaches == 0` is the refusal), and `shmdt` now also unmaps (best-effort, never reported). Linux's `do_shmat` has no SHM_DEST check; X11Libre's `ProcShmAttach` returns BadAccess instead, so **every MIT-SHM client -- every GTK app, and the whole XFCE shell -- was dying on this**. Proven by `.wfgy/shmprobe4.sh` (run `shmp4c`: `[rmid_held] shmat ok ... read=b'HELLO-LITEBOX'`, `[rmid_dead]` still EINVAL) and by `appm2`. **Rule: a segment dies at RMID only once `attaches == 0`.**
- `aca3a53` a `write(2)` past an object's page-rounded capacity **grows the one store instead of clipping to the object** (`memfd_write_through`, `file.rs`), closing old open item 1c. `.wfgy/memfdgrow.sh`: 1MB into a memfd last `ftruncate`d to 0 is seen by `pread@4096`, `pread@tail`, an `mmap` tail and a fork child. Remaining, unmeasured: a mapping established BEFORE a growth still points at the old object (`resize_memfd_shared_backing` must create a new one -- a Windows mapping's size is fixed at creation).
- `9f7c994` **A sized memfd is ONE store**: the shared OBJECT is the store; the in-mem file is only `fstat`'s size plus the fd position. Install-path (`install_shm_file`) and `mmap` must both hit the object.
- `575f0e2` an fd with no name AND no shared object yet (a `memfd_create` fd before its first `ftruncate`) is carried as a byte snapshot instead of refusing the fork. **Rule: an uncarriable fd returns NO errno -- it silently drops the fork off the cross-process path** onto the RELOCATING fallback, which faults the child before one instruction (`Exception(14) cr2=<stale low addr> error_code=0x7`, `rip` off by 0x1860000). `LITEBOX_PROCESS_FORK_IGNORE_FDS` (`process.rs:4074`) = "carry what can be carried, lose the rest". **Never run the stack with fork OFF** (`-ExtraEnv "LITEBOX_PROCESS_FORK="`): every child then dies that way, controls included, so fork-OFF is not a valid control.
- `f7d0f79` SysV shm attachments drop at process exit (`detach_sysv_shm_on_process_exit`, `mm.rs:533`). `b6e1142`+`1503276` segments live until `shmctl(RMID)`: backing store is a real file (`<spill>/sysvshm/<name>.bin`) made at `shmget`, unlinked at RMID/last detach. Traps: open it with `FILE_GENERIC_EXECUTE` (a section's protection ceiling comes from its file handle's rights); `win32_err=5` = VIEW LONGER THAN SECTION (grow the OBJECT).
- `f5d73ff` the flock(2) registry lives per host process (`lib.rs:3605`), not on byte-shared `GlobalState`: a fork child inheriting inline bytes read garbage `BTreeMap` nodes (`btree/node.rs:1232: range end index 65529 out of range for slice of length 11`, child rc=137, zero output). **That panic correlated with LAUNCH ORDINAL, so every "X kills chromium" A/B in that window measured the ordinal, not the variable.** Per-process is right here -- unlike `drm`/`evdev` (Open 4).
- `31ca26b` `MAX_INLINE_WAITERS` 32->128 (`platform/lib.rs:6671`): a waiter queue sized for one guest is not sized for a 38-process session. `1732ad9` a carried-pipe pump could outlive its child (`Option<usize>` collapsed "nothing yet" into EOF); reads are three-way `ForkPipeRead` (`litebox/src/platform/mod.rs:1549`). `463dc29` **never drain a pipe the guest holds for itself** (libuv's GLOBAL SIGNAL LOCK is `read(pipefd[0],&c,1)`; forwarding is now only for the carried end that IS the child's stdin). `16f3e76` **no path holding `net_lock` may block** (`litebox/src/net/mod.rs:862`). `5b7ff62`/`42c6099` `ShimTransport::connect` drops `net_lock` before its spin_loop; queued bytes reach smoltcp before `close(2)`. `a1423ee` HOLDING a pipe end is not READING it (`timeout`/`env`/`nohup`/`setpriv` keep stdin open): `pending_bytes` (FIONREAD) breaks that wait. `7d2a6a7` `SHARED_UNIX_CONN_CAPACITY` 1024->4096 (`unix.rs:3726`) + every unadopted-carry discard releases the sender's slot hold: chromium renders with its own sandbox active. `efce1a5` `/proc` enumerates the whole guest session (`guest_pids=30`; before it **1** in a 62-process session). `bb518ca` a new per-child env var needs a remove after adoption.

## How to run and drive it (harness lessons that cost sessions)

- **No WSL, no hypervisor, ever.** The runner is a NATIVE Win32 exe; host tooling is PowerShell or Git Bash. Every litebox launch is `CREATE_NO_WINDOW`.
- Cheap repro: `target/release/litebox_runner_linux_on_windows_userland.exe -Z --oci-image docker.io/library/debian:stable-slim -- /bin/bash -c '<script>'`. PowerShell, never Git Bash, for guest paths; single quotes only inside `-c`; redirect with `cmd /c "... < script.sh > out 2> err"`. Build ONLY `cargo build --release -p litebox_runner_linux_on_windows_userland`. **Never pipe a build through `tail`** (BUILD_RC then reads tail's status).
- Full stack: `.wfgy/pass118_full.ps1 -Run <name> -MaxSeconds N` (+`.sh`); waits for 2.5GB free and terminates every `litebox_runner` at its cap -- a stale older driver kills a newer run.
- Cheap guest repro: `.wfgy/guest2.ps1 -Script <sh> -Run <name> -Secs <n>` (script to a guest `bash -s` on STDIN). Sets `LITEBOX_PROCESS_FORK=1`, `LITEBOX_LAZY_FILE_MAP=1`, `LITEBOX_OCI_USE_LAST_RESOLVED=1`; `-ExtraEnv "K=V;K2=V2"`, `-Publish "8081:8081,9222:9222"`, `-Exe <other build>`; writes `.wfgy/<Run>.out`/`.err`. `rc=137` at the END of a run is the harness cap, not a bug.
- **Cargo cannot relink while a runner holds the exe** (`Access is denied. (os error 5)`, BUILD_RC=101). Kill every runner first; if the lock persists with no owner, **rename it** (a rename succeeds on a mapped image): `Move-Item -Force <exe> <exe>.prev`, build, then delete `.prev`.
- **Check the binary is NEWER than the commit you are testing.** chrD24 ran a `00:28` exe while `1503276` landed at `00:36`. `git log -1 --format=%cd <sha>` vs `ls -l --time-style=full-iso target/release/...exe`.

- Script hygiene: launching a `.ps1` from bash mangles `\` (`-File .\.wfgy\x.ps1` arrives as `..wfgyx.ps1`, exit 127) -- use absolute forward-slash paths or the PowerShell tool. Guest scripts must be LF: CRLF turns every `\`-continued line into its own command. `sleep 45; ...` is blocked by the harness -- use `until grep -q "RUN COMPLETE" ...; do sleep 5; done`.

## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole guest session). Refusal errno is API contract: EPERM lets callers degrade, EINVAL/ENOSYS fails them hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check (never `PrintWindow`/`CopyFromScreen`). Never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A mutable table on the `SharedUnixAddrPresenceTable` pattern needs every write path mirrored to the shared side.
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`, `platform/lib.rs`); carried: pipes/regular files/eventfds/pty/unix sockets; dropped: cloexec + pty fds; **NOT carried at all: shared-memory mappings (Open 1), inet sockets**. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6, `lib.rs:3931`) gates the spawn and fails open after 8s, because each child rebuilds the OCI rootfs in its own heap. Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it. The post-duplication clone site is SUPERSEDED (`process.rs:6206`) -- believe `try_cross_process_fork`'s log. Every ineligible fork is logged at `warn` under the default `LITEBOX_LOG`.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot roots every task sharing that state, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets over blanket module debug. Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`, `LITEBOX_PROCESS_FORK_IGNORE_FDS`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Dispatched subagents: Sonnet, not Opus. Web search: Google, not DuckDuckGo; if blocked, camoufox; never DDG.

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` (`process.rs:4994`) spawns a host thread (`platform/lib.rs:13842`) blocking on the child's INITIATING THREAD handle (not the process: extra OS threads can outlive the task), then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. `sys_wait4` (`process.rs:3067`) re-polls every 15ms instead of trusting the notify; on reap it runs `import_cross_process_writable_layer` (a real tar read). `waitpid(-1)` only sees entries registered in THIS host process -> ECHILD.
- SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it. `signalfd` never wakes -- nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`); `pidfd_open` (`inotify.rs:353`) does.
- The external fault watchdog (`process_fork.rs`) polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. Gated on the sticky event `Local\litebox-fault-armed-<pid>` (a NULL `OpenEventW` handle means ALWAYS ARMED); LATENT false positive.

## Other subsystems (merged, not re-verified this pass)

- **Linux runner (`litebox_runner_linux_userland`):** cloud sessions boot `webtop:debian-xfce` (`--initial-files rootfs.tar --rewrite-syscalls --uid 0 --gid 0 --pid1 --tun-device-name tun0 ... /bin/sh /init`) into s6, Xvfb, XFCE, nginx, pulseaudio, dbus, Selkies; host browser at `http://10.0.0.2:3000` (TUN, host 10.0.0.1). Native fork (`has_native_fork()==true`): shared state must live in the arena; the thread-based fork corrupts guest memory on Linux.
- **Shared memory and locks:** `RawMutex` = a pointer-free wait queue + cross-process `Event`s with `holder_pid` dead-holder recovery (`bff1d0b`), chunking waits to `LIVENESS_CHECK_INTERVAL` (2s). A 128MiB `shared_kernel_arena_alloc` (anything at/above `SHARED_KERNEL_HEAP_BASE` `0x7FF8_0000_0000`, `platform/lib.rs`) backs `SharedArc<T>`, which shares only `T`'s inline bytes -- so shared registries are fixed-slot atomic tables (`SharedUnixConnTable`'s arena slice, `unix.rs:4326`).
- **File visibility:** a file one host process wrote is invisible to siblings until it exits. `file_spill.rs` write-through-spills `SPILLED_PREFIXES` (`file_spill.rs:10-18`) to `%TEMP%\litebox-spill-<rootpid>\<slot>.bin`; extend the prefix LIST, not the mechanism -- do NOT add `/tmp/`. Direction matters: a fork child gets the parent's exported writable layer AT SPAWN, and its own writes reach the parent only when it exits and `wait4` imports them -- so a fork carry of a fresh `/tmp` fd works and the same fd over SCM_RIGHTS does not (`only_in_own_writable_layer`, `9412184`). Fs permissions follow the calling task's fsuid/fsgid (`set_effective_identity`); root bypasses rwx bits; anything walking the fs outside a syscall must run inside `with_root_identity` (`d428acd`). Only the newest `Source` bridge drains.
- **OCI:** `litebox_packager --oci-image <ref> --output <tar>` pulls, merges and rewrites every ELF; the runner does the same in memory (`.litebox-cache/`, keyed by `REWRITER_CACHE_VERSION`). `linuxserver/webtop:debian-xfce` and `ubuntu-xfce` ship XFCE.

## Guest stack: chromium + selkies

MILESTONE (chr21/22): `.wfgy/guest2.ps1 -Script .wfgy/chr15.sh -Run chr21` (webtop, no `--no-sandbox`) -> `CHROME_PIPELINE_DONE rc=0`; 6x `Activated seccomp-bpf`, ZERO `No usable sandbox!`.
- **TWO chromium failure modes -- do not merge them.** (a) `Crashing due to FD ownership violation:` + `zygote_host_impl_linux.cc:129] No usable sandbox!` = the `CanCreateProcessInNewUserNS()` probe. (b) rc=133 (SIGTRAP) with NO sandbox line = crashpad/HOME.
- **A `HOME` chromium shares with anything root ran kills it**: a root-run app makes `$HOME/.config` 0755 root, so uid 911 gets `stat $HOME/.config/chromium/Crash Reports: Permission denied (13)`; crashpad mkdirs only its LAST component, so a missing chain is ENOENT (2). Fix: `mkdir -p $HOME/.config/chromium; chmod -R 777; chown -R 911:911` on a HOME nothing else touched -- `chmod 777` on a SHARED HOME is NOT enough.
- NON-ROOT (`setpriv --reuid 911 --regid 911 --init-groups`); `--user-data-dir` `chmod 777` when a root shell created it (else `SingletonLock: Permission denied`, exit 21). `HOME=/tmp/cuhome` exits 0 (`.wfgy/cpad1.sh`); `--crash-dumps-dir` does not exist in Debian's build.
- `seccomp(2)` is real: a classic-BPF interpreter (`syscalls/seccomp.rs`) on the raw syscall number at the top of `Task::do_syscall`; `SECCOMP_RET_TRAP` must RETURN the syscall number (`ad2659f`), payload in `si_errno` (`067367b`).
- **CDP from inside the guest is the decisive chromium probe** (`.wfgy/chrdesk38.sh`, `/tmp/cdp.py`): `GET http://127.0.0.1:9222/json/list` (launch chromium with `--remote-debugging-port=9222 --remote-allow-origins=*`), then a RAW websocket (stdlib only: `socket`+`base64` handshake, masked client frames, `struct` length parsing -- the image has no websocket-client package) for `Page.enable`, `Runtime.evaluate` (`document.readyState`, `document.title`, `getComputedStyle(document.body).backgroundColor`, `innerHTML.length`) and `Page.captureScreenshot`. Decode the PNG in-guest with `zlib` + the five filter types and census it there. `Page.captureScreenshot` is chromium's OWN compositor output, so it separates "chromium never rendered" from "X/selkies never captured it" -- which no pixel census of the stream can do. (Caveat that does NOT apply here: a HOST browser's CDP `take_screenshot` cannot see a `<video>` -- two shots 2 min apart at 40fps were BYTE-IDENTICAL, mean RGB (0,0,0).)
- **XWD grab: field 11 is NOT the stride.** `bytes_per_line` is field **12**, RGB masks **14/15/16**, pixels start at `len(raw) - w*h*bpp`, pixel words little-endian when `byte_order == 0`. Correct reader: `/tmp/xwd.py` in `.wfgy/chrdesk16.sh`-`19.sh`. **Every `blue=0.00%` from chrD19 and earlier is INVALID.** And that `start` can be off by ONE byte, which rotates the channels: (246,245,244)/(244,246,245)/(245,244,246) are all the SAME flat #f6f5f4 grey. Judge flat fills with a sorted-channel compare, not an exact RGB match, and dump the centre pixel's hex.
- **A file a fork child wrote is visible only to the shell that reaps it**: a headless `--screenshot` must run chromium in the FOREGROUND of its subshell with the analysing python after it in that SAME subshell (`.wfgy/chrdesk8.sh`). Blue PNG = compositor fine; white PNG = no frame.
- Never `--enable-logging=stderr --v=1` in a long run (chrD13 stopped painting while the stream held 32-37fps). Windowed recipe: `xfconf-query -c xfwm4 -p /general/use_compositing -s false`, `xsetroot -solid "#305070"`.
- xfce4-session takes ~120s to register its WM (`WM_POLL n=24`); until then `xprop -root _NET_SUPPORTING_WM_CHECK` answers "not found" and the stream is a legitimately black root.
- SELKIES 2.0.0 BINDS 8080, NOT 8081; `CUSTOM_WS_PORT` is a 1.x name it ignores, so `--port=8081` must be explicit. It ENABLES BASIC AUTH BY DEFAULT and, with no password set, STOPS ITS OWN SERVER -- always `--enable-basic-auth=false` or set `PASSWORD`.
- **A host browser reaches a guest SERVER only through `-p/--publish h:g`**: the runner's network is OUTBOUND NAT only (why chrD23 got `ERR_CONNECTION_REFUSED` while the guest's own `curl` read `code=200`).
- **selkies' capture REQUIRES MIT-SHM at the X server**: pixelflux's X11 path is NvFBC -> DRI3 -> XShm and `run_shm_capture` HARD-FAILS on `shm_query_version` (`pixelflux/src/x11/mod.rs:1097-1138`, `:1198-1201`) -- no XGetImage fallback, no flag. On failure the client connects then hits `ERROR:ws:FATAL: Initial reconfiguration completed, but video pipeline did not start` (`src/selkies/websockets_mode.py:3936`); the real diagnosis is the line above it, `Failed to start capture for 'primary': <e>` (`:5685`). Knobs: `PIXELFLUX_DEBUG=1` (the `[X11] Res:` lines are `debug!`-gated), `--encoder jpeg`, `--gpu-id -1 --use-cpu true`. After a FATAL, `video_active` stays set and `VIDEO_STOPPED` goes out, so re-pressing `Play Stream` retries.
- A log selkies writes under `/tmp/` is INVISIBLE to the launching shell -- pipe it: `( selkies --debug 2>&1 | sed 's/^/[selk] /' ) &`. A/B on ONE port is useless (`kill -9` on a wedged cross-process child does not reap it -> `Address already in use`).
