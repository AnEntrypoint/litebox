## Standing lessons and hard constraints

- Guest-reachable code returns an errno, never a panic (the host process IS the whole guest session). Refusal errno is API contract: EPERM lets callers degrade, EINVAL/ENOSYS fails them hard.
- `LITEBOX_DUMP_FRAMES=1` is the only trustworthy `--gui` visual check (never `PrintWindow`/`CopyFromScreen`). Never time litebox with one host process per datapoint (a bare spawn costs 1.6-2.3s), and never subtract timestamps across a parent and a fork-child log (`init_logging()` resets elapsed time per child).
- A `TypedFd` index is valid only against the `Descriptors` that inserted it; shared-memory structs must hold no process-relative pointers. A mutable table on the `SharedUnixAddrPresenceTable` pattern needs every write path mirrored to the shared side.
- Cross-process fork (`LITEBOX_PROCESS_FORK=1`): a genuine `D==0` fork (`spawn_cross_process_fork_child`, `litebox_platform_windows_userland/src/lib.rs:13886`); carried: pipes/regular files/eventfds/pty/unix sockets; dropped: cloexec + pty fds. `cross_process_fork_slots` (`CROSS_PROCESS_FORK_SLOT_COUNT` 6, `litebox_shim_linux/src/lib.rs:3908`) gates the spawn and fails open after 8s, because each child rebuilds the whole OCI rootfs in its own heap (~350MB-1.1GB). Slots are keyed by child host pid, freed at STARTUP-COMPLETE not at reap (`a24ce9d`). The env var is PRESENCE-CHECKED (`var_os`): `=0` still ENABLES it.
- `chroot(2)` is real (`e608959`): `FsState.root` is shared by `CLONE_FS`, so a chroot on any task sharing that state roots all of them, parent included; `cwd` is root-space, dirfd-relative paths stay unrooted. Do NOT test `CLONE_FS` with a raw `clone(CLONE_VM|CLONE_VFORK|CLONE_FS)` from CPython (parent never resumes, dies 139); use pthreads.
- Logs: default `warn,...fork_verify=error`; prefer dedicated low-overhead targets over blanket module debug. Verbosity comes from `LITEBOX_LOG`, not `RUST_LOG`.
- Env: `LITEBOX_PROCESS_FORK`, `LITEBOX_LAZY_FILE_MAP`, `LITEBOX_IDLE_TRIM=0`, `LITEBOX_OCI_USE_LAST_RESOLVED`, `LITEBOX_DUMP_FRAMES`; diagnostics `LITEBOX_DIAG_LOCKSTALL`, `_WAIT_DUR`, `_LOCKSTALL_TRACE`, `_ALLOC_STACK`, `_MEM_BREAKDOWN`, `_FAULT`, `_WATCHDOG`, `_NO_FAULT_WATCHDOG`, `_NO_EXTERNAL_FAULT_WATCHDOG`, `LITEBOX_DIAG_SOCKET_READ_TARGET`.
- Dispatched subagents: Sonnet, not Opus. Web search: Google, not DuckDuckGo; if blocked, camoufox; never DDG.

## Child exit: how a parent learns (and how it can fail)

- `arm_cross_process_exit_notifier` (`litebox_shim_linux/src/syscalls/process.rs:4938`) spawns a host thread (`litebox_platform_windows_userland/src/lib.rs:13658`) blocking on the child's INITIATING THREAD handle, then pushes SIGCHLD into `process.shared_pending` + `interrupt_all_threads()`. It waits on the THREAD because extra OS threads can outlive the task.
- `sys_wait4` (`process.rs:3062`) re-polls every 15ms (`:3081`) instead of trusting the notify; on reap it runs `import_cross_process_writable_layer` (`:3175`, a real tar read). `waitpid(-1)` only sees entries registered in THIS host process, so a grandchild is invisible -> ECHILD (`:3239`).
- SIGCHLD is dispatched only when the thread passes `check_for_interrupt`/`prepare_to_run_guest` (`litebox_shim_linux/src/wait.rs:41-64`), so anything driving reaping off SIGCHLD alone (glib) can miss it. `signalfd` never wakes: nothing calls `pollee.notify_observers()` from the push path (`signalfd.rs:185-191`, `:218-225`); `pidfd_open` (`inotify.rs:353`) does.
- The external fault watchdog (`process_fork.rs:5185`) polls every 500ms and `TerminateProcess`es a process whose CPU delta stayed <=10ms for 15s. Gated on the sticky event `Local\litebox-fault-armed-<pid>`, set only by the two VEH self-terminate paths (`lib.rs:2319`, `:2623`) -- a NULL `OpenEventW` handle means ALWAYS ARMED (`:5247`/`:5251`). LATENT false positive (a healthy `Xvfb` in `select()` qualifies), not the observed killer.

## Cross-process shared memory and locks

`RawMutex` = a pointer-free wait queue + cross-process `Event`s with `holder_pid` dead-holder recovery (`bff1d0b`); waits chunk to `LIVENESS_CHECK_INTERVAL` (2s). A 128MiB `shared_kernel_arena_alloc` (any mutex at/above `SHARED_KERNEL_HEAP_BASE` `0x7FF8_0000_0000`, `litebox_platform_windows_userland/src/lib.rs:11552`, is cross-process) backs `SharedArc<T>` (`GlobalState`, `Network`, pty/unix tables); `SharedArc::new` shares only `T`'s inline bytes (a `BTreeMap`'s nodes live on the private heap), so shared registries are fixed-slot atomic tables -- why `SharedUnixConnTable`'s slots moved to an arena slice (`unix.rs:4326`). `litebox::sync::RwLock` is writer-preferring -- a QUEUED writer blocks readers.

## Cross-process file visibility, identity, apt

- A file written by one host process is invisible to siblings until it exits (per-process writable layer). `syscalls/file_spill.rs` write-through-spills `SPILLED_PREFIXES` (`file_spill.rs:10-18`) to `%TEMP%\litebox-spill-<rootpid>\<slot>.bin` (1024 slots): apt's two dirs + five chromium paths. Extend the prefix LIST, not the mechanism -- do NOT add `/tmp/`; the spill dir is never cleaned up.
- Direction matters: a fork child receives the parent's exported writable layer AT SPAWN; its own writes reach the parent only when it exits and `wait4` imports them (`litebox-forkwrite-*.tar`). So a fork carry of a fresh `/tmp` fd works and the same fd over SCM_RIGHTS does not; `only_in_own_writable_layer` (`9412184`) is how the carry path tells them apart.
- The fs layers check permissions against the calling task's fsuid/fsgid (`litebox::fs::set_effective_identity`); root bypasses rwx bits. Anything walking the fs outside a syscall (export/import) must run inside `litebox::fs::with_root_identity` (`d428acd`).
- Fork children inherit cwd and full credentials; a child's deletions reach the parent as `.wh.` tar entries; only the newest `Source` pipe bridge of a read end drains.

- **TWO DISTINCT failure modes -- do not merge them.** (a) `Crashing due to FD ownership violation:` + `zygote_host_impl_linux.cc:129] No usable sandbox!` = the `CanCreateProcessInNewUserNS()` probe (`pipe()` + `clone(CLONE_NEWUSER)`, fds in `base::ScopedFD`). (b) rc=133 (SIGTRAP) with NO sandbox line = crashpad/HOME -- chrD31's `CHROMIUM_A_EXIT rc=133` was (b).
- **A `HOME` chromium shares with anything root ran kills it** (`crhome1`, chrD27/28/31). A root-run app (xfce4-terminal, thunar, mousepad -- anything writing `~/.config`) makes `$HOME/.config` 0755 root, so chromium's uid 911 gets EACCES: `stat $HOME/.config/chromium/Crash Reports: Permission denied (13)`. Crashpad derives that path from HOME and mkdirs only its LAST component, so a missing chain is ENOENT (2) and the browser dies on the same CHECK. Fix both: `mkdir -p $HOME/.config/chromium; chmod -R 777; chown -R 911:911` on a HOME nothing else touched; `chmod 777` on a SHARED HOME is NOT enough. Both look identical from outside: xterm/xcalc paint, `blue=0.00%`, `CHROMIUM_EXIT` in the first minute.
- Must run NON-ROOT (`setpriv --reuid 911 --regid 911 --init-groups`); `--user-data-dir` must be `chmod 777` when a root shell created it (else `SingletonLock: Permission denied` = exit 21). A writable `HOME=/tmp/cuhome` exits 0 (`.wfgy/cpad1.sh`); `--crash-dumps-dir` does not exist in Debian's build.
- `seccomp(2)`/`prctl(PR_SET_SECCOMP)` are real: a classic-BPF interpreter (`syscalls/seccomp.rs`) on the raw syscall number at the top of `Task::do_syscall`; mode, `no_new_privs` and the filter stack live on `Process`. `SECCOMP_RET_TRAP` must RETURN THE SYSCALL NUMBER (`ad2659f`); its 16-bit payload lands in `si_errno` (`067367b`). What unblocked rendering: `SHARED_UNIX_CONN_CAPACITY` 1024->4096 (`7d2a6a7`).
- Still open: (1) the launcher thread SERIALISES cross-process spawns, so children hit the 15s "no connection" self-termination; (2) `--single-process` dies on a CHECK in `RenderProcessHostImpl`; (3) `Vmem::duplicate` skips `VM_OWN_FORK_PADDING` (SAME-process fork); (4) ~1/run `rebuilding a carried SCM_RIGHTS fd failed errno=ENOENT` (leveldb LOG); (5) GWP-ASan `MapRegion` EEXIST occasionally.
- **Reading an XWD grab: field 11 is NOT the stride.** `bytes_per_line` is field **12**, RGB masks **14/15/16**, pixels start at `len(raw) - w*h*bpp`, pixel words little-endian when `byte_order == 0`. Correct reader: `/tmp/xwd.py` in `.wfgy/chrdesk16.sh`-`19.sh` (18/19 ported 2026-10-04; a run launched BEFORE the port prints bogus `bpl=24 bpp=3`, e.g. chrD26). **Every `blue=0.00%` from chrD19 and earlier used shifted fields and is INVALID.**
- **A file a fork child wrote is visible only to the shell that reaps it**, so a headless `--screenshot` must run chromium in the FOREGROUND of its subshell with the analysing python after it in that SAME subshell (`.wfgy/chrdesk8.sh`). Blue PNG = compositor fine, fault is the X11 presentation path; white PNG = no frame ever produced.
- **Never run chromium `--enable-logging=stderr --v=1` in a long run**: chrD13's desktop stopped painting (94-95% black, xterm included) while the stream held 32-37fps. Windowed recipe: `xfconf-query -c xfwm4 -p /general/use_compositing -s false`, `xsetroot -solid "#305070"`, control `xterm -bg #ff0000 -fg #ffffff -geometry 40x10+60+560` (`.wfgy/chrdesk5.sh`/`6.sh`); chrD12/D13's "paints its own UI and nothing else" was WITH `--disable-dev-shm-usage` -- superseded.
- UNRESOLVED: `9014df7` reported "chromium headless prints example.com"; diff `9014df7..HEAD` before assuming anything about Mojo.

## Selkies / host-browser visibility -- WORKING (chrD8)

- CDP `take_screenshot` CANNOT SEE A `<video>` SURFACE: two shots two minutes apart at 40fps were BYTE-IDENTICAL, mean RGB (0,0,0). Capture with JS `drawImage(video)` + `toDataURL('image/png')`, decoded host-side (`.wfgy/chrD8_frame.png`). A black screenshot is not evidence of a broken stream.
- xfce4-session takes ~120s to register its WM (`WM_POLL n=24`); until then `xprop -root _NET_SUPPORTING_WM_CHECK` answers "not found" and the stream is legitimately a black root. Even after the WM is up, allow ~60s of stream time (1b).
- SELKIES 2.0.0 BINDS 8080, NOT 8081; `CUSTOM_WS_PORT` is a 1.x name it ignores, so `--port=8081` is explicit. It ENABLES BASIC AUTH BY DEFAULT and, with no password set, STOPS ITS OWN SERVER (`Basic authentication is enabled but no password was set` then `Stopping service: websockets`) -- always `--enable-basic-auth=false` or set `PASSWORD`.
- **A host browser reaches a guest SERVER only through `-p/--publish h:g`**: the runner's network is OUTBOUND NAT only. `guest2.ps1` had no `-p` until 2026-10-04, which is why chrD23 got `ERR_CONNECTION_REFUSED` while the guest's own `curl` read `code=200`.
- **selkies' capture REQUIRES MIT-SHM at the X server.** pixelflux's X11 path is NvFBC -> DRI3 -> XShm and `run_shm_capture` HARD-FAILS on `shm_query_version` (`pixelflux/src/x11/mod.rs:1097-1138`, `:1198-1201`) -- no XGetImage fallback, no flag to select one; also `require_32bpp` (`:239`). chrD24: client connects then `ERROR:ws:FATAL: Initial reconfiguration completed, but video pipeline did not start`, no `[X11] Res:`/`EncFPS` ever, `video.readyState=0`; the FATAL (`src/selkies/websockets_mode.py:3936`) is an immediate post-check with no timeout, and the real diagnosis is the line above it, `Failed to start capture for 'primary': <e>` (`:5685`/`:5329`). Knobs: `PIXELFLUX_DEBUG=1` (the `[X11] Res:` lines are `debug!`-gated), `--encoder jpeg`, `--gpu-id -1 --use-cpu true`; upstream's Xvfb line uses `-shmem -noreset`. Click `Enable Video Stream`/`Play Stream` before any `<video>` gets a track; after a FATAL the server keeps `video_active` and sends `VIDEO_STOPPED`, so a re-press retries.
- A log selkies writes under `/tmp/` is INVISIBLE to the launching shell -- pipe it: `( selkies --debug 2>&1 | sed 's/^/[selk] /' ) &`. A/B on ONE port is useless (`kill -9` on a wedged cross-process child does not reap it -> `Address already in use`). Set `loop.set_exception_handler` in every guest probe script (aio9).
