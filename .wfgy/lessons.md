## 2026-07-30 -- EVP_MD_fetch/apk SIGSEGV root cause found and fixed (RELR + double-relocation of ld.so); transition{to:EXECUTE} stuck loop again post-fix, same class as the earlier FSM-desync entry above

**CORRECTION, found ~20 minutes later in the SAME session:** the "32-bit truncation of a stack slot" root-cause claim recorded for the ash-hang PRD row (`ash-hangs-after-fork-in-and-and-compound-commands`) was itself a debugging-tool artifact, not a real litebox bug: `gdb -batch` on this Windows-hosted gdb build treats `long` as 32-bit (LLP64/Windows convention, not the LP64 a Linux-hosted gdb would use), so `print/x *(long*)($rsp+8)` silently truncated a genuine 64-bit stack pointer to its low 32 bits, producing a garbage-looking `0xff542430` value that looked exactly like real corruption. A raw `x/2gx $rsp` memory dump (no C-style cast, no `long` involved) read the SAME memory correctly as `0x00007fffff542430` -- a perfectly well-formed 64-bit stack address. The underlying hang is still real and still reproduces, but the root cause is different from what was first written up: `g_parsefile` is stuck at its own static initial value (`&basepf`) while the `stop` argument is a real, different, non-`basepf` address, so `popfile()`'s `if (pf == &basepf) return;` early-out means the loop spins forever doing nothing rather than advancing. See the PRD row's corrected text for the full, updated finding. Generalizes to: on ANY Windows-hosted gdb session, never trust a `print/x *(long*)ptr` or similar C-cast-based read for a 64-bit value -- always use `x/gx`/`x/2gx` (a raw memory-examine command, unaffected by gdb's own `long` type width) instead, or explicitly cast through `(long long*)`/`(unsigned long long*)` if a C-style cast is truly needed. This cost real investigation time chasing a phantom truncation bug before the raw-memory read caught the discrepancy.
