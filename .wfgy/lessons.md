The panic source (`litebox_platform_linux_userland/src/lib.rs:~3023`) `assert_eq!(old_sa.sa_sigaction, SIG_DFL, "signal {sig} handler already installed")` for SIGINT/SIGALRM fired because POSIX mandates a backgrounded/nohup/supervised process inherits SIGINT under SIG_IGN -- so litebox (which must own the guest's signal dispositions) blew up purely from its launch context, poisoning its static `Once`. The first false lead was blaming a "two-copy linker issue" (nm proved exactly one `register_exception_handlers`/`Once` symbol); the real cause was the overly-strict SIG_DFL assertion.
Fix / resolution: replace the `assert_eq!(...SIG_DFL)` with an `assert!` that tolerates `SIG_DFL` OR `SIG_IGN` (both benign inherited dispositions) while still surfacing a genuine pre-existing custom handler as a conflict. Re-ran the full shim suite single-threaded AND parallel, detached (SIGINT=SIG_IGN): both now pass `186 passed; 0 failed` (16 filtered: `test_mremap` + `tun`, since this container has no `/dev/net/tun`). The prior parallel SIGSEGV also vanished.
Generalizes to: any Linux process that is expected to run under a non-interactive launch context (background job, `nohup`, a session/supervisor, a test harness spawning it detached) must not assume SIGINT/SIGALRM arrive at SIG_DFL -- POSIX inheritance makes SIG_IGN the norm for such processes. Guarding against "signal already installed" via `== SIG_DFL` is wrong unless you also accept `SIG_IGN`; otherwise the codebase is unreachable exactly in the deployment scenarios that matter. Also a re-confirmation of the project's recurring meta-lesson (first plausible-looking read of a diagnosis is often wrong): a single-symbol `nm` check correctly refuted the "two copies of the code" theory, and the actual bug was a one-line over-strict assertion.
